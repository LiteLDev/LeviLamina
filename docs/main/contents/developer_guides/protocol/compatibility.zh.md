# 协议兼容性

只要协议参与是可选的，LeviLamina 就会保留原汁原味的普通 Minecraft 登录过程。协商仅在专用 LeviLamina 服务器与远程 LeviLamina 客户端之间发生，且两端都必须启用协议并广播合法的发现标记（Discovery Marker）。

## 端点矩阵

| 客户端 | 服务器 | 策略 | 结果 |
| --- | --- | --- | --- |
| 启用 LL 协议 | 启用 LL 协议 | 必需声明相互兼容 | 协议协商完成，随后 Minecraft 登录完成，会话变为活跃状态。 |
| 启用 LL 协议 | 原版 | 任意 LL 客户端策略 | 原版登录继续进行；客户端将对端归类为非协议对端，且不创建会话。 |
| 原版或禁用协议 | LL | `requireLoader: false` | 原版登录继续进行，不进行协商，亦不创建会话。 |
| 原版或禁用协议 | LL | `requireLoader: true` | 服务器拒绝登录，并提示加载器兼容性原因。 |
| 启用 LL 协议 | 禁用 LL 协议 | 协议禁用时 `requireLoader` 不生效 | 表现为普通的非协议 Minecraft 行为；无协议钩子或会话。 |
| 任意本地客户端组合 | 本地世界 | 任意 | 在版本 1 中归类为非协议连接。 |

一旦 LL 握手开始，任何超时、畸形消息、摘要不匹配或不兼容的必需声明都会被视为协议失败。端点在承诺参与协商之后，绝不会静默将该连接降级为原版连接。

对于不兼容的 LL 对端，服务器在关闭连接前会发送致命协议错误代码以及有界的诊断信息。断开连接数据包还会附带面向用户的提示原因；若缺少必需模块，提示中会包含其完整的模块 ID。预期的兼容性失败和被拒绝的对端流量不会在服务器上作为加载器错误记录。本地内部错误、编解码器回调错误以及传输层失败仍会作为错误级别的诊断日志记录。

## 加载器策略与模块策略的区别

服务器端 `requireLoader` 控制连接中的客户端是否必须参与 LeviLamina 协议发现。它并不强制要求客户端安装每一个特定的模组或模块。

服务器端 `requiredModules` 是一个包含完整模块 ID（例如 `example:gameplay`）的列表。列表中列出的每个模块都必须存在于服务器声明中，并被提升为强制要求客户端提供兼容的声明。配置中出现无效、重复或本地缺失的 ID 均属于配置或协商错误，绝不会被忽略。

模块声明自身提供了跨端点的需求策略：

| 需求策略 | 导致协商失败的缺失端点 |
| --- | --- |
| `Optional` | 都不导致失败；如果无法找到兼容项，则直接禁用该模块。 |
| `RequiredOnClient` | 客户端。 |
| `RequiredOnServer` | 服务器。 |
| `RequiredOnBoth` | 任一端点。 |

如果两端声明均存在，但其模块协议范围或必需特性不兼容，则非可选模块会导致协商失败。可选模块则会被直接禁用。

`requiredModules` 影响的是模块协商，而非原版发现流程。如果服务器必须拒绝任何没有安装 LL 加载器的客户端，请同时启用 `requireLoader`。

## Payload 兼容性

仅当满足以下条件时，Payload 才能协商成功：

- 其所属模块已启用；
- 两端声明了完全相同的完整 Payload ID；
- 两端声明在方向和确定性运行时 ID 上达成一致；
- 模式版本集合中至少存在一个共同支持的版本。

协商会选出共同支持的最高模式版本。协商后的最大编码数据体大小取客户端声明、服务器声明、协商传输层配置和协议硬性上限中的最小值。

如果不兼容或缺失的 Payload 是 `Optional`，则该 Payload 会被禁用。如果任一声明将其标记为 `Required`，其所属模块将被禁用；而当该模块本身也是强制要求时，整个协商将宣告失败。模组代码在假定某项可选能力存在之前，必须先检查 `SessionView`。

## 模块内部的特性（Feature）

特性拥有稳定的本地名称、版本范围以及 `required` 标志。仅当两端均声明了该特性且版本范围存在重叠时，特性才会被启用；协商选取共同支持的最高版本。

缺失或不兼容的可选特性将被直接忽略。任一端点标记为必需的特性若缺失或不兼容，会导致所属模块变为不兼容；随后该模块的需求策略将决定是禁用该模块还是握手失败。

在原本兼容的模块内部，对于相互独立的可选行为，请使用特性进行管理。当某个组件需要拥有自身的生命周期或需求策略时，请使用独立的模块。

## Minecraft 与模组版本差异

协议兼容性并不覆盖 LeviLamina 支持的 Minecraft 版本矩阵或原生 ABI 要求。仅当客户端和服务器模组所声明的网络传输契约存在实际重叠时，它们才可以使用不同的实现构建版本。切勿将 C++ 内存布局、RTTI 名称或动态链接库 ABI 作为跨进程的 Payload 格式。

有关向后兼容的演进模式，请参阅[协议版本控制](versioning.zh.md)；有关支持的部署范围，请参阅[限制与约束](limitations.zh.md)。
