# 协议版本控制

该协议具有若干个相互独立的分层版本机制。将它们解耦可使模组能够演进其协议 Payload，而无需将每次修改都与 LeviLamina 的核心握手版本捆绑在一起。

## 版本分层

| 分层 | 声明者 | 用途 |
| --- | --- | --- |
| 核心协议版本 | LeviLamina | 控制消息、协商规则、记录（Transcript）以及信封封装语义。 |
| 模块语义化版本 | `ModuleDefinition::version` | 模组所有的模块声明的信息性版本。 |
| 模块协议范围 | `ModuleDefinition::protocolVersions` | 整个模块级网络契约的兼容修订版本范围。 |
| 特性版本范围 | `FeatureDefinition::versions` | 单个可选或必需能力的兼容修订版本范围。 |
| Payload 模式 | `PayloadDefinition::schemas` | 单个 Payload ID 的确切编码字段布局与含义。 |

协商后的 `SessionView` 记录了所选的核心协议版本、模块协议版本、特性版本以及 Payload 模式。模块语义化版本不能用作模式兼容性的替代判断依据。

## 稳定 ID 与运行时 ID

模块与 Payload 的文本 ID 是公开的网络身份标识：

```text
example:gameplay
example:gameplay/set_label
```

LeviLamina 会确定性地将完整的 Payload ID 哈希为运行时 ID（Runtime ID）。该哈希值是一个高效的传输槽位标识，既不是由模组选择的版本号，也不是用于避开命名冲突的后门。协商流程会校验文本身份与运行时 ID 是否一致，并在发生冲突时采取“故障即关闭”（Fail-closed）策略。

C++ 类型名称、命名空间、RTTI 拼写、字段内存偏移量以及编译器 ABI 均不参与这两个稳定的文本 ID 构建。

## 兼容的模式演进

假设模式 1 编码以下内容：

```text
u32 entityId
string label (最大 64 字节)
```

较新的实现可以增加模式 2：

```text
u32 entityId
string label (最大 64 字节)
bool persistent
```

在兼容过渡期内，注册 `.schemas = {1, 2}` 并实现两套编解码器分支。两个新对端会选定模式 2；而一个新对端与一个旧对端则会选定模式 1。后续移除模式 1 是有意终止与仅支持模式 1 的对端的兼容性。

切勿在仍称为模式 1 的格式末尾追加布尔值字段。解码器要求完整消费所有输入，因此旧版解码器会正确拒绝尾随的附加字节。

不要求升级模式的兼容变更包括：内部 C++ 代码重构、更快的校验逻辑以及保留了既有接受字节含义的 Bug 修复。通常需要升级新模式的变更包括：添加/删除字段、改变字段顺序或整数宽度、改变单位、改变规范字符串规则，或者改变某数值是否可选。

## 模块协议演进

`ModuleDefinition::protocolVersions` 用于为整个模块级的网络契约标记版本；它独立于 LeviLamina 核心握手版本。当某项兼容性变更影响到多个 Payload 或行为之间的协同工作方式，且无法通过单一 Payload 模式或可选特性清晰表达时，请使用该版本范围。

在兼容过渡期内，声明诸如 `{1, 2}` 的范围，并支持为每个会话选定的行为。`NegotiatedModule::protocolVersion` 包含两端共同支持的最高版本。只有在明确终止对旧版模块协议的支持后，才提高版本下限。

切勿因内部实现调整、单个 Payload 布局变更或独立可选能力而递增模块协议版本。针对这些情况，应使用更细粒度的模式版本或特性版本。

## 特性演进

引入新的可选行为时，应将其声明为具有确定回退机制的可选特性。在灰度发布期间，声明实现所能实际处理的所有特性版本；协商会选出两端共同支持的最高版本，并将其记录在该会话的 `NegotiatedFeature::version` 中。

仅当不再支持旧版行为时，才提高特性的版本下限。移除某个可选特性的声明会导致在与仍声明该特性的对端协商时将其忽略。移除任一端点标记为必需的特性，或导致其不兼容，会使所属模块变为不兼容，因此请根据模块需求策略妥善协调该变更。

特性版本改变的是能力语义，而非 Payload 字节结构。如果启用新的特性修订版本同时改变了 Payload 布局，请引入新的 Payload 模式，并显式定义模组所接受的特性与模式组合。

## 何时创建新的 Payload 或模块

当某项操作的本质含义发生改变，而不仅仅是表示形式变更时，应创建全新的 Payload ID。例如，`set_label` 和 `patch_entity_metadata` 不应仅仅因为一个可以模拟另一个就共享同一个 ID。

当一组功能需要独立的需求策略、兼容范围或所有权生命周期时，应创建新的模块。如果无关功能会独立演进，请避免创建一个包罗万象的单一庞大模块。

切勿将已移除的 Payload ID 复用于全新的语义。注册表保留了墓碑标识（Tombstone）和方向信息，以防止在进程内发生不安全的反向激活；但跨版本的网络兼容性同样依赖于模组对已发布 ID 的尊重与规范。

## 需求策略演进

将可选的模块、特性或 Payload 收紧为强制必需，可能会直接拒绝先前能够成功连接的对端。请将其视为部署策略变更，并在发布前对两端进行统筹协调。

推荐采用以下发布顺序：

1. 在两端发布新能力，均设置为可选并具备兼容的回退行为；
2. 允许各安装实例逐步升级，并观察协商后的能力可用情况；
3. 仅在后续协调一致的发布中，当确定有意拒绝旧版对端时，才将该能力收紧为必需。

服务器端的 `requiredModules` 设置可以在不重新编译模块的情况下强制部署某个模块，但前提是服务器实际注册了该模块。

## 大小限制演进

协商后的数据体限制是两端声明值与传输配置三者中的最小值。调高本地限制并不能强迫旧版对端接受更大的消息。发送方必须在当前会话协商出的限制范围内进行编码。

仅当所有已声明模式的每一个合法编码值仍能容纳在新限制中时，缩减限制才是网络兼容的。如果旧有的合法值可能超出新限制，请作为语义兼容性破坏变更进行协调，或引入新的有界表示形式。

编解码器规则请参阅[创建协议 Payload](creating_payload.zh.md)，协商失败矩阵请参阅[协议兼容性](compatibility.zh.md)。
