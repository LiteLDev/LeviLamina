# 协议限制与约束

本页面界定了 LeviLamina 协议版本 1 支持的范围。即使特定运行时测试看似可行，也绝不能依赖超出此范围的行为。

## 支持的部署拓扑

受支持的拓扑结构为：使用匹配受支持的 Minecraft 和 LeviLamina 版本的专用 LeviLamina 服务器与远程 LeviLamina 客户端。

以下拓扑结构在版本 1 中**不受支持**：

- 本地世界（单人世界）托管；
- 在客户端目标端内部激活服务器角色的协议端点；
- 假定单个目标端中同时存在客户端和服务器协议 API 的通用模组二进制文件；
- 将本地玩家连接作为两个客户端组件之间的协议会话使用。

本地世界仍表现为普通的非协议 Minecraft 会话，即使两端碰巧安装了相同的客户端模组也是如此。

## 线程模型

仅支持从相应的端点游戏线程执行发送：

- 客户端到服务器的发送使用客户端游戏线程；
- 服务器发送、定向扇出和广播使用服务器线程；
- Payload 处理器在接收端点的游戏线程上内联执行。

不支持在任意线程上调用发送。协议层不包含隐式协议队列、执行器上下文跳转、重试或背压等待。在其他线程产生工作的模组必须显式在相应的 LeviLamina 线程执行器上调度有界任务，并在该任务实际运行时重新校验会话的有效性。

处理器必须保持有界且非阻塞。在处理器内部执行阻塞式 I/O、无界解析或等待其他游戏线程任务，都可能导致端点卡顿甚至死锁。

## Payload 大小与传输模型

默认的最大编码数据体限制为 `Limits::DefaultPayloadBody`（256 KiB）。Payload 定义可以选择更小的值，或者最高提升至 `Limits::MaxPayloadBody`（8 MiB）。超出此硬性上限的值将被直接拒绝。

这些限制描述的是编码后的协议数据体，而非重组后的完整 Minecraft 数据包。Minecraft 自身也存在与传输方向相关的数据包大小限制以及帧头开销。Payload 必须为其封装信封留出足够的余量，绝不能将 8 MiB 的协议上限视为传输层的承诺保证。

版本 1 在一个协议封装信封中发送一个逻辑 Payload。它**不提供**：

- `BulkTransfer` API；
- 透明分片或重组；
- 多消息事务机制；
- 流式数据体；
- 断点续传；
- 磁盘缓存缓冲。

## 协商与注册表变更

协商在登录期间发生。不支持在活跃会话上进行动态重新协商。

请在所属模组的常规初始化阶段注册协议模块和 Payload。对相关注册项的修改将使现有协商好的会话失效，而不是就地改变其协商契约。重新连接会创建一个新的世代，并重新执行完整的协商。

注册对象是仅支持移动的所有权令牌。销毁或重置令牌会撤销该注册。模组必须在需要开放其协议表面的整个生命周期内保留这些令牌。

## 传输层与身份鉴权

协议不会替代或扩展 Minecraft 原有的身份验证、鉴权授权、数据加密、压缩、可靠性、保序、拥塞控制、数据包分片或连接所有权管理。协商成功的模块仅证明对端声明了兼容的 LeviLamina 协议表面；它不会赋予任何游戏操作权限。

Payload 处理器仍必须对照常规的服务器端游戏状态，对远程玩家或操作进行鉴权。**绝不能仅仅因为客户端请求的 Payload 通过了协议层校验就盲目信任该请求**。

## 兼容性保证

稳定的模块与 Payload 名称、方向、需求策略、模式版本以及编码后的含义，都是模组网络兼容性契约的一部分。C++ 类型名称、对象内存布局、RTTI 拼写以及编译器 ABI 绝不是网络层标识符。

以下行为属于**不受支持**的使用方式：

- 依赖于从 C++ 类型名称派生的运行时 ID；
- 在缺少兼容解码器的情况下更改现有模式的含义；
- 在相反的方向上发送 Payload；
- 假定在断开连接、超时、注册表变更或重新连接后会话仍保持活跃；
- 在未检查会话视图的前提下，直接假定可选的模块或 Payload 已协商成功。
